## 二、为什么要做

### 1. 晚报缺失：这不是偶发，是每天都在丢内容

检查 97 期历史数据（按 `updatedAt` 逐期核对）发现：

- **8-29 ~ 9-24（26 天）完全正常**：晨报 08:1x、晚报 18:1x
- **9-25 起开始漂移**，9-26 之后 **26 期在凌晨 00:00–05:49 生成**
- **17 期缺失**（其中 15 个晚报、2 个晨报）

**根因**：GitHub Actions 的定时实际触发时间会比 cron 晚数小时。旧脚本用"跑的那一刻几点"判断版次（`hour < 14` → 晨报），18:00 的晚报任务一旦被延迟跨过午夜，就会被写成"**第二天的晨报**"——
于是前一天的晚报永久缺失，同时第二天的晨报被提前到凌晨发布（读者早上打开看到的是凌晨生成的内容）。
更糟的是 22:00 的兜底任务本身也被延迟到次日凌晨，它只检查"新的一天"，所以补不回来。

**影响**：网站每 2 天就少一期内容，且历史缺口**无法事后补**（脚本只保留当天新闻，事后重跑会拿今天的新闻冒充旧日期，属于污染档案）。所以必须改逻辑，不能靠补数据。

**修复后**：无论延迟多久，脚本都能算出"该补哪期"，延迟只会让某期晚出，不会再丢内容。线上实测：一次 `topup` 运行把 10-19 的晚报补上了（23 条），今天的晚报也正常生成（26 条）。

### 2. 本地副本落后线上：随时可能"改错文件"

比对 8 个核心文件的 SHA256 后发现 7 个一致，唯独 `.github/workflows/daily.yml` 本地是旧版——只有 2 个 cron，缺 08:05/18:05 补跑和 22:00 兜底，也缺 `PUSHPLUS_TOKEN` 注入。
按"改本地 → 上传"的流程操作时，一旦上传这个文件，就会把线上 5 个触发点**一键退化成 2 个**，兜底能力消失。

另外本地 `site/data` 停在 8-25（落后 55 天），本地 git 是 1 个提交、无 remote、分支叫 `master`（线上是 `main`）——根本无法正常推送。**这正是你之前"git push 报错"的根源**。

### 3. 工作目录权限被卡死：连删文件都做不到

`D:\智能体生成` 这条链上的目录权限只给了当前用户"写入"，**没有"删除"**（历史沙箱遗留的 ACL）。表现是：新建文件可以，删除/重命名任何文件都报"访问被拒绝"。
这会让任何"整理项目"的操作都做不下去（包括清理垃圾文件、移动废弃目录）——所以必须先修权限，否则重构无从谈起。

### 4. 行情卡片在误导读者

`COMEX 黄金(期货)` 的 `id` 不匹配 `sh/sz/hk` 前缀，从来不参与实时抓取，但页面把它当实时数据显示 **+10.00%**——每个读者都会以为"今天黄金又涨了 10%"。这属于低级但很伤信任的问题。
（顺带修掉了另一个隐患：如果直接回补历史期，会把"今天的行情"写进历史序列，走势图会被污染，所以回补期强制不写行情历史。）

### 5. 仓库卫生与安全

- 根目录混着 5 个腾讯云废弃目录（455 KB）、23 个编辑工具残留的临时目录、4 个废弃配置文件——看着像在跑，其实全是死的，容易改错对象
- `_local-archive/tencent-cloud/digest-server/` 里有**明文密钥**（腾讯云 API Key、Cookie 签名密钥）；已确认**从未上传 GitHub**，但留在磁盘上是隐患

## 四、可以继续做的优化（按性价比排序）

### P1 · 建议尽快做（影响读者体验 / 运维可靠性）

| 建议 | 怎么做 | 收益 |
|---|---|---|
| **补齐偏薄板块的新闻源** | `NEWS_SOURCES` 里给 `education` / `economy` / `internet` 各补 1–2 个稳定源（候选：教育部/统计局官网、财新、界面、第一财经、虎嗅备用源） | 现在教育板块常年 1–2 条、10-19 晨报出现"互联网大厂 0 条"；补源是最直接的提升 |
| **加"跨板块 URL 去重"** | 脚本层在送模型前按 URL 去重（现在只按 URL 去重素材，但模型仍可能把同一事件写进两个板块） | 提示词已要求"同一事件只出现一次"，但靠模型自律；脚本层加校验成本极低 |
| **加运行状态文件** `site/data/status.json` | 每次运行写：上次运行时间、模式、生成期次、各源成功/失败数、缺口情况 | 现在"有没有跑、缺不缺期"只能去 Actions 翻日志；写了状态文件就能在页面脚注显示，也能被外部监控 |
| **缺口巡检 + 告警** | 每天 22:00 那次运行结束后检查"当天 08/18 是否都在"，缺则用现有 PushPlus 通道推一条告警 | 现在失败是"静默"的（只有 GitHub 邮件），有了告警才知道该手动补 |
| **给脚本加最小 CI** | 加一个 `.github/workflows/check.yml`：PR/push 时跑 `node --check` + `planTargets()` 单测 | 这次改的是核心逻辑，最怕以后手滑改坏；单测很便宜 |

### P2 · 体验与长期治理

| 建议 | 说明 |
|---|---|
| **日期选择器改用下拉列表** | 现在用 `<datalist>` + `type=date`，必须手动输入日期才出建议，体验一般；换成按 archive 渲染的 `<select>` 更快 |
| **加"上一期/下一期"按钮** | 现在切换期次要点日期 + 版次两个控件 |
| **修掉过期文案** | 无数据提示写的是"本网站自 2026-08-19 起每日自动生成"，日期硬编码且已不准，改成读 `archive.json` 最早日期 |
| **数据归档策略** | 现在 99 期共 1.5 MB，日均新增约 26 KB（≈ 0.76 MB/月、9.3 MB/年）。Pages 限额 1 GB 短期无忧，但 git 每次提交都是全量快照、历史会累积。可考虑"保留最近 90 天明细 + 更早按年月合并/压缩" |
| **移动端检查** | 卡片网格在窄屏下的换行、字号没专门验证过 |
| **前端自定义自选** | 现在改 `watchlist.default.json` 要重新部署；可用 localStorage 让读者自己加股票 |
| **输出 RSS** | 顺便生成 `site/data/rss.xml`，别人可以订阅；成本很低 |
| **密钥打理** | 这次用的 PAT 用完即删；以后建议用**细粒度 token + 7 天有效期**，或干脆用 GitHub Desktop（浏览器授权，不碰 token）。`LLM_KEY` 也建议定期轮换 |
| **清理腾讯云残留** | 控制台确认 `digest-secure` 环境是否仍在计费；确认后删掉 `_local-archive/tencent-cloud/digest-server/`（含明文密钥） |

### 不建议做（想清楚再动）

- ❌ **回补历史 15 期**：会用今天的新闻冒充旧日期，污染档案，比缺失更糟。
- ❌ **把定时改成每分钟/高频核查**：GitHub 免费额度有限，且内容源本身是按天更新，5 个触发点已足够。
- ❌ **把行情做成真正的实时推送**：免费行情接口的实时性有限，写"静态参考值"比假装实时更诚实。
